  `.select()` query builder as the `.insert()` argument to get `INSERT INTO ... SELECT`). This
  keeps the "invisible until submitted" and "frozen after submitted" rules structurally
  guaranteed rather than relying on route-level filtering or the upstream command's own guards.
- No new event types needed - `OrderLineAdded`/`OrderLineChanged`/`OrderLineRemoved`/

- `npm run run:checks -- --staged` passed cleanly; split into `feat:` code commit then local-only
  status update (`chore:` commit), per the established slice-scope-guard pattern.

**Learnings for future iterations:**
- A read model that must stay invisible until a later "commit" event, then show a value frozen at
  that moment (KitchenQueue's submission snapshot), needs a working table plus a separate frozen
  table - not just the working table filtered by a `submitted` boolean (that's OrderPad's own,
  different shape, where the row is visible throughout and only gains a flag). Copy the working
  rows into the frozen tables via knex's `insert(selectQueryBuilder)` (produces `INSERT INTO ...
  SELECT`) at the triggering event, rather than joining/filtering the working table at query time -

- A STATE_VIEW's own `dependencies[]` omitting an event that a sibling slice with a similar shape

  signal, not an oversight - it means this read model doesn't need that event's fields at all
  (KitchenQueue never shows `serverName`/`openedAt`), reinforcing the existing "only react to
  declared dependencies" rule rather than copying a sibling's dependency list wholesale.

- knex's object-form join alias (`.join({alias: tableName}, ...)`) is incompatible with a

  needing to exist yet — same as the existing "not every unbuilt cross-context event emitter is
  a blocker" rule, just applied to a same-context sibling slice's own event instead of a
  cross-context one.
