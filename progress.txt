## 2026-09-23 - HoldTableForReservation

- Picked next-highest-priority Planned slice in Day7 context: HoldTableForReservation (AUTOMATION).
- Read slice.json: the processor has no `triggerEvent` — like RemindersDue/SendReservationReminder,
  it is a polling automation with `fields: []` and its only INBOUND dependency is the
  `AutoSeatingCandidates` READMODEL. Every command field

  `AutoSeatingCandidates.*`.
- `AutoSeatingCandidates` was blocked in the previous iteration (commit `13555a4`) pending a
  table-capacity data-source decision, and as a result has **no code at all** — verified with
  `grep -rn "AutoSeatingCandidates" src/slices/` (no matches) and no projection/migration file
  exists. Building `processor.ts` here would require inventing the very table schema that slice

- This is the same root-cause ambiguity propagating downstream, not a new independent one — the

  fully specified and unambiguous, but the processor cannot be built without guessing
  AutoSeatingCandidates's shape. Escalated via `request-feedback`:
  - Found the board by matching the slice id (`c4df296d-03bd-4579-8ee4-d65186b32cab`) via
    `mcp__eventmodelers__list_slices` across the org's boards — landed on board
    `62c1fe42-f280-4fe4-9700-26c085a63d12` ("markus.beck").
  - Posted a QUESTION comment (`c14517db-633d-4af5-8e8e-f03930050ea1`) on the slice asking whether
    it should stay blocked until AutoSeatingCandidates is unblocked and built, or whether a
    different/interim polling source is intended.
  - Set status to `Blocked` on the board via `mcp__eventmodelers__update_slice_status`.
  - Mirrored `Blocked` status locally in `.build-kit/.slices/day7/index.json` and
    `.build-kit/.slices/day7/holdtableforreservation/slice.json`.
- No code was written. No branch was merged. Deleted the empty `feature/holdtableforreservation`
  branch created at the start of this iteration.

**Learnings for future iterations:**
- A processor with `fields: []`, no `triggerEvent`, and a single INBOUND READMODEL dependency is a
  *polling* automation (see RemindersDue/SendReservationReminder pattern) — it drains rows from
  that read model on a schedule rather than reacting to an event. If that upstream read model is
  Blocked/unbuilt, the polling automation cannot be built either — check the upstream read model's
  status in index.json before starting an AUTOMATION slice whose only dependency is a READMODEL.
- Root-cause blockers propagate: once one slice is blocked for a data-model reason, every
  downstream slice whose command fields map exclusively from that slice's read model is blocked
  too. Don't re-litigate the same ambiguity per-slice — reference the earlier block in the new
  question instead of re-deriving it.
- The local `.build-kit/.eventmodelers/config.json` is absent in this project, but the *root*
  `.eventmodelers/config.json` and `.mcp.json` still resolve MCP credentials — `connect`'s "skip
  platform communication if config.json is absent" instruction in Ralph's CLAUDE.md refers
  specifically to the build-kit-local file; MCP tools worked fine here. Use
  `mcp__eventmodelers__list_boards` + `list_slices` to find which board a given slice id lives on
  when the config file doesn't pin one.

## 2026-09-23 - HoldTableForReservation (retry after unblock)

- Board had resolved the previous blocker: AutoSeatingCandidates was built (commit `5355bac`) and
  HoldTableForReservation's own status was back to `Planned`. Started from `day12`.
- Implemented as an AUTOMATION with a polling processor (no `triggerEvent`, single INBOUND
  dependency on the `AutoSeatingCandidates` READMODEL) — same pattern as
  RemindersDue/SendReservationReminder: `HoldTableForReservationCommand.ts` (stream key
  `Day7-table-{tableNumber}`, the same stream `BlockTable` uses, so a block and a hold on the same
  table see one another — copied the overlap-checking `decide`/`evolve` shape directly from
  `BlockTableCommand.ts`), `processor.ts` (drains `AutoSeatingCandidates` rows with
  `autoSeatingOutcome: 'Pending'` every minute, walks table numbers 1–20 ascending, issues the
  command for the first untried table, treats `table_blocked`/`table_already_held`/
  `hold_already_exists` as expected rejections that just move to the next table number, DLQs
  anything else).
- `HoldTableForReservation`'s own error codes (`table_blocked`, `table_already_held`,
  `hold_already_exists`) are new — not copied from BlockTable's — since the two commands reject
  for the same reason but through a distinct command name; slice.json's specifications didn't name
  the codes explicitly, so they were derived from each spec's `description`.
- 5 tests (one per specification), all passing.
- No `routes.ts` — automations have no HTTP surface (per build-automation skill), so no `@openapi`
  block was needed here.
- FF-merged into `day12`. Board slice status InProgress → Done via
  `mcp__eventmodelers__update_slice_status` (board `62c1fe42-f280-4fe4-9700-26c085a63d12`, slice
  `c4df296d-03bd-4579-8ee4-d65186b32cab`).

**Learnings for future iterations:**
- A polling automation whose upstream READMODEL exposes an enum-like status field (here
  `autoSeatingOutcome: 'Pending'`) drains rows filtered by that status, same as RemindersDue
  filtering by its due-time predicate — the row itself, not a separate queue table, is the
  work list.
- When a table-number range has no backing "published table configuration" data (see
  AutoSeatingCandidates's own resolution — no seat-capacity concept exists in this codebase), a
  processor that must "walk table numbers" can only use a fixed bound; 1–20 here matches the
  numbers already used across BlockTable/TableStatus test fixtures and board examples. This is a
  processor-internal implementation constant, not a slice.json field, so it doesn't need a
  slice.json entry — the command still takes `tableNumber` as an opaque string per spec.

- Picked next-highest-priority Planned slice in Day7 context: ConfirmHeldReservation (AUTOMATION).

- Read slice.json: a polling processor (`fields: []`, no `triggerEvent`, single INBOUND dependency
  on the `HeldReservations` READMODEL) — same shape as HoldTableForReservation polling
  AutoSeatingCandidates. Its command fields map exclusively from `HeldReservations.*`, and its
  specifications' given/then mix `TableHeldForReservation`/`TableHoldReleased`/`ReservationConfirmed`
  in the same stream — the only way `decide()` can see all three to run its guard checks is if the
  command is keyed by `tableNumber` on the shared `Day7-table-{tableNumber}` stream
  (BlockTable/HoldTableForReservation's stream), not by `eMail` on the Day6 guest stream. The
  not-yet-built ReleaseTableHold slice's own spec ("Reject releasing a hold for a reservation that
  is already confirmed") confirms this: it needs ReservationConfirmed visible on that same table
  stream too.
- Implemented: `ConfirmHeldReservationCommand.ts` (stream key `Day7-table-{tableNumber}`, `decide`
  rejects `hold_not_found` / `hold_already_released` / `already_confirmed`, otherwise appends the
  existing Day6 `ReservationConfirmed` event), `processor.ts` (drains all `HeldReservations` rows
  every minute — the read model's own purpose is "still waiting for its second-step checks", so
  every row it holds is confirmable; `already_confirmed`/`hold_already_released` are treated as
  expected races with the projection, not DLQ-worthy errors).
- No new event type needed — `ReservationConfirmed` already exists in `Day7Events.ts` (Day6's own
  event, re-exported).
- No `routes.ts` — automation, no HTTP surface.
- 4 tests (one per specification), all passing (pure decide/evolve, no Testcontainers needed for
  this file).
- `npm run run:checks -- --staged` passed cleanly on the first attempt with only `src/slices/**`
  staged.
- FF-merged into `day12`. Board slice status → Done via `mcp__eventmodelers__update_slice_status`
  (board `62c1fe42-f280-4fe4-9700-26c085a63d12`, slice `52705c29-f758-46bb-8f89-e113277300bd`).
  Forgot to set InProgress on the board before starting this iteration — went straight from
  Planned to Done at the end; no claim conflict resulted, but future iterations should call
  `update-slice-status` to InProgress as the very first step per Ralph's CLAUDE.md.

**Learnings for future iterations:**
- When a polling automation's specifications mix events from more than one emitter on the same
  `given`/`then` (here TableHeldForReservation + TableHoldReleased + ReservationConfirmed), check
  whether they all already live on one shared stream before assuming the command should key off
  the read model's own id field (`reservationCode`) — if the command's `decide` needs to see all of
  them to run its guards, it must replay the stream they actually share (here the table stream,
  `Day7-table-{tableNumber}`), same pattern as HoldTableForReservation.
- A downstream slice still `Planned` (ReleaseTableHold here) can carry a specification that reveals
  which stream an upstream command must use — its "reject releasing an already-confirmed hold"
  check only makes sense if ReservationConfirmed lands on the same stream ReleaseTableHold itself
  will read from. Read forward into still-Planned sibling slices' specs when a stream-key decision
  is ambiguous from the current slice alone.
